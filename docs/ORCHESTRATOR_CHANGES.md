# Paper — زیرساخت و رفتار Orchestrator: تاریخچهٔ تغییرات

> سند مرجع برای مرور تغییرات زیرساختی که تاکنون روی رفتار «Tri-Agent Orchestrator» و
> چرخه‌ی حیات ایشوها در این ریپو اعمال شده. همهٔ فایل‌های ذکرشده **در ریپو** هستند
> (commit شده و روی `origin/main` موجودند) مگر آن‌که صریحاً «خارج از ریپو» گفته شود.

---

## ۱. نقشهٔ فایل‌های زیرساخت (همگی در ریپو)

| فایل | نقش |
|---|---|
| `orchestrator.py` | حلقه‌ی اصلی اجرا: انتخاب تسک، dispatch ایجنت، verification، commit، مدیریت ایشو |
| `issue_bot.py` | Triage/دروازه‌ی تأیید ایشوهای گیت‌هاب و واردکردن آن‌ها به `ROADMAP.json` |
| `issue_lifecycle.py` | قوانین مشترک مسیریابی ایشو (لیبل‌های نادیده، تطبیق تسک↔ایشو، بستن) |
| `roadmap_store.py` | نوشتن اتمیک و قفل‌دار `ROADMAP.json` (جلوگیری از race در ذخیره) |
| `watchdog.sh` | cron هر ۲ دقیقه: revive اورکستر/webhook، پاک‌سازی منابع، استال‌چک، deploy |
| `webhook_server.py` | شنونده‌ی webhook گیت‌هاب (رویداد issues/issue_comment → reconcile فوری) |
| `make_queue.py` | گیت‌های انتشار مرحله‌ای برای ابتکار «Paper Make» (ایستگاه‌های #18..#41) |
| `maintainers.json` | لیست تأییدکنندگان مجاز (moslembabaee) و کلمات `/approve` |
| `tests/test_make_queue.py` | تست گیت صف Make |
| `tests/test_decompose.py` | تست رفتار پدر/فرزند و decompose |

## ۲. تاریخچه‌ی گام‌به‌گام (از ابتدا تا الان)

### گام ۱ — پایه: وب‌هوک + دروازه‌ی تأیید مالک (کامیت `21c01fc`)
- معرفی `webhook_server.py` (رویدادهای `issues` و `issue_comment` گیت‌هاب).
- مدل اجرای «فقط با تأیید مالک»: تسک فقط با لیبل `approved` یا کامنت `/approve` اجرا می‌شود.
- پیش‌نیاز cron/watchdog برای زنده نگه‌داشتن daemon ها.

### گام ۲ — Decompose خودکار + سقف ۲۵ نوبت + گزارش blocked (کامیت `0c61c3a`)
- تسک‌های بزرگ (>۵۰۰ کاراکتر یا چندبخش) به ۲-۴ زیرتسک شکسته می‌شوند (`T-ISSUE-N-1..4`).
- سقف نوبت ایجنت: `--max-turns 25`.
- وقتی همه‌ی ایجنت‌ها شکست می‌خورند: لیبل `blocked` + کامنت خطا روی ایشو (به‌جای سکوت).

### گام ۳ — ضدعفونی زیرساخت: نادیده‌گرفتن لیبل‌های infra و پاک‌سازی in-progress (کامیت `9733431`)
- ایشوهای با لیبل `infra/ops/documentation/manual` توسط issue_bot نادیده گرفته می‌شوند
  (در `issue_lifecycle.py`: `IGNORED_LABELS`).
- `issue_lifecycle.py` و `roadmap_store.py` از همین‌جا جداسازی شدند (قوانین مشترک + نوشتن قفل‌دار).
- هنگام بستن ایشو، لیبل‌های `in-progress,blocked` به‌صراحت حذف می‌شوند.

### گام ۴ — دروازه‌ی تأیید غیرفعال شد (تصمیم مالک، در کد `issue_bot.py`)
- **هر ایشوی جدید بدون AI-triage خودکار `approved` می‌شود** (کامنت: «approval gate disabled by owner»).
- AI triage (تحلیل Architect) رد شد؛ ایشو مستقیم وارد صف می‌شود.
- (این تغییر در commit های میانی باگ‌ها همراه بود — گام ۷ آن را اصلاح می‌کند.)

### گام ۵ — Paper Make: گیت انتشار وابسته‌به‌زنجیره (کامیت `f6df9d9` به‌بعد)
- `make_queue.py`: از ۲۴ ایشوی Make (#18..#41) هر بار **فقط یک ایشو** آزاد می‌شود.
- شرط آزادسازی: ایشوی قبلی بسته + تسک محلی completed + CI کامیت دقیق همان ایشو سبز.
- ایشوهای بعدی با لیبل `manual` نگه داشته می‌شوند تا نوبت‌شان برسد.
- تست: `tests/test_make_queue.py`.

### گام ۶ — زنجیره‌ی ایجنت و سلامت مدل
- ترتیب اولیه: `claude → antigravity → codex`؛ بعداً با سنجش شکست‌ها جابه‌جا شد.
- در `watchdog.sh`: چک 503 مدل و سوییچ خودکار به مدل پشتیبان (بعداً حذف شد — گام ۹).
- سقف مهلت هر ایجنت ابتدا ۶۰۰ ثانیه؛ بابت تسک‌های سنگین خیلی کم بود (گام ۱۰ اصلاح شد).

### گام ۷ — اصلاح باگ «blocked برای همیشه» (در `issue_bot.py`)
- با گیت غیرفعال، ربات قبلاً ایشوهای `blocked` را بی‌درنگ دوباره approve می‌کرد →
  حلقه‌ی بی‌پایان retry روی یک تسک شکست‌خورده.
- **رفتار جدید: ایشوهای `blocked` نگه داشته می‌شوند** («held for maintainer review») و فقط
  با اقدام صریح مالک (`/approve` یا حذف لیبل) دوباره فعال می‌شوند.
- این مهم‌ترین اصلاح ضد-حلقه است.

### گام ۸ — بستن باگ «failover دروغین» (در `orchestrator.py`)
- **مشکل:** `execute_agent_task` فقط کلود را اجرا می‌کرد؛ لاگ «Attempting antigravity/codex»
  می‌نوشت ولی در عمل باز همان کلود را با همان مدل صدا می‌زد → ۳ بار کلود تکراری، بدون failover واقعی.
- **اصلاح:** dispatch واقعی هر سه ایجنت با فرمان‌های مجزا.

### گام ۹ — حذف سوییچ خودکار مدل از watchdog (در `watchdog.sh`)
- `sed` که تنظیمات کلود را به `ag/gemini-3.8-flash-high` برمی‌گرداند **حذف شد** —
  چون هر ۲ دقیقه تنظیمات درست را بازنویسی می‌کرد (رقابت با انتخاب دستی مدل).

### گام ۱۰ — حالت «فقط کلود» + مهلت ۴۰ دقیقه (تصمیم مالک)
- `AGENT_CHAIN = ["claude"]` — همهٔ تسک‌ها فقط با کلود اجرا می‌شوند.
- `timeout=2400` (۴۰ دقیقه) برای کلود تا تسک‌های سنگین وسط کار قطع نشوند.
- `--max-turns 80`.
- (این‌ها هم در `origin/main` موجودند.)

### گام ۱۱ — Decompose پیش از dispatch با پدر به‌عنوان ایست بازرسی (در `orchestrator.py`)
- قبل از اجرا: اگر تسک «بزرگ» است (توضیح >۶۰۰ کاراکتر یا چندبخش) → به ۲-۴ فرزند شکسته می‌شود.
- **پدر حذف نمی‌شود:** با وضعیت `decomposed` و لیست `children` در صف می‌ماند.
- هر فرزند: `parent_id` + `subtask_index/total_subtasks` + شماره‌ی ایشوی پدر.
- **پس از اتمام همه‌ی فرزندان، پدر فقط یک بار verification می‌شود** (`maybe_finalize_parent`):
  - موفق → پدر `completed` + کامیت + بستن ایشوی پدر.
  - شکست → پدر `blocked` + کامنت روی ایشو.
- پدر هرگز دوباره به ایجنت داده نمی‌شود.
- تست: `tests/test_decompose.py` (۴ تست: تشخیص بزرگ، حفظ پدر، لینک فرزند، verify نهایی).

## ۳. رفتار فعلی (خلاصه‌ی یک‌نگاه)

**چرخه‌ی هر تسک:**
```
approved در ROADMAP/GitHub
  → اگر بزرگ: decompose به فرزندان (پدر decomposed، فرزندان approved)
  → dispatch به claude (فقط کلود، مهلت ۴۰ دقیقه)
  → اگر exit=0: verification نهایی (npm test && build)
  → موفق: کامیت + push + بستن ایشو (+ اگر فرزند بود: چک پدر)
  → شکست کامل زنجیره: لیبل blocked + کامنت → ایشو می‌ماند تا اقدام مالک
```

**قوانین issue_bot:**
- ایشوهای `infra/manual/ops/...` → نادیده.
- ایشوهای `blocked` → نگه داشته می‌شوند (فقط با `/approve` مالک آزاد می‌شوند).
- ایشوهای جدید → خودکار `approved` (بدون AI triage).
- تسک‌های completed → ایشو بسته + پاک‌سازی لیبل‌ها.

**watchdog (هر ۲ دقیقه):**
- زنده‌کردن اورکستر/webhook در صورت مرگ.
- پاک‌سازی رم/دیسک.
- استال‌چک بر اساس آخرین commit (>۳۰ دقیقه).
- اجرای issue_bot + auto_deploy + make_queue.
- (برای توقف کامل، cron فعلاً پاک شده — در صورت نیاز دوباره نصب می‌شود.)

## ۵. نکات/محدودیت‌های شناخته‌شده (برای ایده‌گرفتن)

1. **فقط کلود = نقطه‌ی تکین:** اگر کلود/9Router از کار بیفتد، کل صف می‌ایستد
   (زنجیره‌ی failover عمداً حذف شده). احتمالاً در آینده «کلود→پشتیبان سالم» بهتر است.
2. **Orphan ایجنت:** وقتی اورکستر kill می‌شود، کلودهای فرزند می‌توانند orphan بمانند و
   روی working tree ادامه دهند (نیازمند پاک‌سازی دستی هنگام ری‌استارت).
3. **Rate limit گیت‌هاب:** فرمان‌های `gh` پشت‌سرهم (به‌ویژه GraphQL) می‌توانند سهمیه را پر کنند.
4. **حالت Make:** گیت انتشار (make_queue) فقط با بستن کامل ایشوی قبلی جلو می‌رود.
5. **۶ فایل app/scene** تغییرات commit نشده‌اند (باقی‌مانده از تسک ناتمام Boolean Vector) —
   تصمیم‌گیری: نگه‌داشتن یا بازگرداندن.
